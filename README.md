# Mini NPU Simulator

코디세이 Pre-course 미션 3. NPU가 수행하는 MAC(Multiply-Accumulate) 연산을 Python으로 직접 구현해,
십자가(Cross)와 X 패턴을 판별하고 크기별 연산 시간을 분석하는 콘솔 시뮬레이터입니다.
NumPy 등 외부 라이브러리 없이 Python 표준 라이브러리(`json`, `time`, `os`, `sys`)만 사용합니다.

## 실행 방법

```bash
python3 main.py                            # 1: 사용자 입력(3×3), 2: data.json 분석
python3 main.py samples/broken_data.json   # (선택) 스키마 오류 처리 검증용 데이터로 모드 2 실행
```

- Windows에서는 `python3` 대신 `python main.py`로 실행합니다.
- 프로젝트 루트에서 실행합니다. Python 3.8 이상.
- `data.json`은 `main.py` 위치 기준 상대 경로로 읽으므로 실행 위치와 무관하게 동작합니다.

## data.json 구조와 처리 규칙

| 항목 | 원본 형태 | 프로그램 처리 |
|---|---|---|
| `filters` 키 | `size_{N}` | N 추출 → 해당 크기 필터 그룹 |
| 필터 라벨 키 | `cross`, `x` | `Cross`, `X`로 정규화 |
| `patterns` 키 | `size_{N}_{idx}` | `split('_')[1]`로 N 추출 → `size_N` 필터 선택 |
| `input` | N×N 2차원 배열 | 키의 N과 실제 크기 일치 검증 |
| `expected` | `+`, `x` | `Cross`, `X`로 정규화 후 판정과 비교 |
| `meta` | 버전 정보 | 사용하지 않음 |

규칙을 위반한 케이스는 예외로 프로그램을 종료하지 않고, 해당 케이스만 FAIL과 사유로 기록합니다.

## 핵심 설계

- **MAC**: 이중 for문으로 `total += pattern[i][j] * filt[i][j]`를 N²번 수행합니다.
- **라벨 정규화**: 입력 시점에 `strip().lower()` 후 매핑 테이블로 `Cross`/`X`로 통일하고, 모르는 라벨은 `None` → FAIL 처리합니다. 콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준입니다.
- **판정 정책**: `abs(score_cross - score_x) < 1e-9`이면 `UNDECIDED`(모드 1에서는 "판정 불가"), 아니면 큰 쪽을 선택합니다.
- **성능 측정**: `time.perf_counter()`로 `mac()` 호출 구간만 감싸 10회 측정 후 평균(ms)을 냅니다. I/O는 측정 구간 밖에 두고, 초기 호출의 편차를 줄이기 위해 측정 전 5회 워밍업합니다.
- **실패 분류**: 모든 FAIL을 `데이터/스키마`, `로직`, `수치 비교` 중 하나로 태그해 출력합니다.

## 결과 리포트

### 실행 결과 요약 (공식 data.json)

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

**전체 6 / 통과 3 / 실패 3** — 실패 3건은 모두 `수치 비교` 분류이며, 데이터/스키마 실패와 로직 실패는 0건입니다.

### 실패 원인 분석

실패 3건은 코드 결함이 아니라 데이터가 의도적으로 동점이 되도록 설계된 케이스입니다.
size_5_1을 예로 들면, X 패턴 입력에 대해 Cross 필터는 가운데 한 칸(0.9)만 겹쳐 `1.0 × 0.9 = 0.9`가 한 번에 계산됩니다.
반면 X 필터는 0.1짜리 9칸을 차례로 누적해 0.9를 만듭니다. 0.1은 2진수로 정확히 표현되지 않는 근사값이라 9번 더하는 동안 오차가 쌓여 `0.8999999999999999`가 됩니다.
즉 수학적으로는 두 점수가 같지만, 계산 경로가 달라 약 1.1e-16의 차이가 생깁니다. size_13_2(차이 2.7e-15), size_25_1(차이 1.8e-15)도 같은 구조입니다.

만약 `>`나 `==`로 비교했다면 size_5_1과 size_25_1은 Cross, size_13_2는 X로 판정되어, 실제로는 동점인데 한쪽이 "이긴" 결과가 됩니다.
그 경우 FAIL 원인이 판정 로직 오류처럼 보여 잘못된 방향으로 디버깅하게 됩니다.
epsilon(1e-9) 비교를 적용하면 세 케이스가 UNDECIDED로 판정되고, expected와 달라 FAIL이 되지만 원인이 `수치 비교`로 정확히 분류됩니다.
1e-9는 이 데이터의 누적 오차(최대 약 3e-15)보다 충분히 크고, 의미 있는 점수 차이(최소 0.1 단위)보다 충분히 작아서 오차만 흡수하고 실제 차이는 구분합니다.

라벨 정규화가 없었다면 판정 결과 `Cross`와 expected `+`가 문자열로 달라 십자가 케이스(size_5_2, size_13_2, size_25_2)가 전부 FAIL이 되었을 것이고, 이는 `데이터/스키마` 문제입니다.
정규화를 입력 시점 한 곳에서 수행해 PASS 3건이 정상적으로 PASS로 집계되었고, 스키마 실패가 0건이 되었습니다.

스키마 검증 경로는 `samples/broken_data.json`으로 확인했습니다. 패턴 크기 불일치(2×3), 알 수 없는 라벨(`circle`), 대응 필터 없음(`size_7`), 키 규칙 위반(`pattern_1`)이 모두 프로그램 종료 없이 `데이터/스키마` FAIL로 기록되고,
공백·대문자가 섞인 `" CROSS "`는 정규화로 `Cross`가 되어 PASS, 기대값과 판정이 다른 케이스는 `로직` FAIL로 분류되는 것을 확인했습니다.

### 시간 복잡도 분석

| 크기 | 연산 횟수(N²) | 평균 시간(ms) | 3×3 대비 시간 | 3×3 대비 N² | 1회 곱셈-누적당 시간 |
|---|---|---|---|---|---|
| 3×3 | 9 | 0.0004 | 1.0배 | 1.0배 | 약 0.044µs |
| 5×5 | 25 | 0.0007 | 약 1.8배 | 약 2.8배 | 약 0.028µs |
| 13×13 | 169 | 0.0036 | 약 9.0배 | 약 18.8배 | 약 0.021µs |
| 25×25 | 625 | 0.0127 | 약 32배 | 약 69.4배 | 약 0.020µs |

*각 크기 10회 반복 평균. 측정 환경: Apple M4 Pro, macOS 26.3, Python 3.14.8. 3회 실행 결과가 5×5 한 번(0.0010)을 제외하고 소수 4자리까지 같았습니다. 절대값은 실행 환경마다 다릅니다.*

MAC은 N×N의 모든 칸을 정확히 한 번씩 방문해 곱셈 1회와 덧셈 1회를 수행하므로, 연산 횟수는 N²이고 시간 복잡도는 O(N²)입니다.
측정 결과도 크기가 커질수록 시간이 단조 증가해 이 추세를 따릅니다.
다만 3×3 대비 25×25가 N² 비율(69배)만큼이 아니라 약 32배만 느린데, 이는 함수 호출, `len()` 계산, 반복문 진입 같은 **크기와 무관한 고정 비용** 때문입니다.
작은 크기에서는 이 고정 비용이 전체 시간에서 차지하는 비중이 커서, 1회 곱셈-누적당 시간이 3×3에서 약 0.044µs로 가장 크게 나타납니다.
크기가 커질수록 고정 비용 비중이 줄어 13×13과 25×25에서는 1회당 시간이 약 0.021µs, 0.020µs로 거의 같아지며, 이 구간(169 → 625, 3.7배)의 시간 비율도 약 3.5배로 N² 비율에 가까워집니다.
즉 시간은 `T(N) ≈ a·N² + b` 꼴이며, N이 클수록 `a·N²` 항이 지배해 O(N²)이 드러납니다.
실제 NPU는 이 N²번의 MAC을 수천 개의 회로로 동시에 처리하지만, 이 시뮬레이터는 for문으로 순차 처리하므로 연산량 증가가 그대로 시간 증가로 나타납니다.

### 대규모 입력(1000×1000) 분석

레포의 `mac`, `mac_flat`, `make_cross`, `measure_ms`를 그대로 import하는 임시 스크립트로 N = 100, 500, 1000을 측정했습니다(스크립트는 레포에 포함하지 않음).
패턴은 `make_cross(N)`, 필터는 `random.random()`으로 원소마다 다른 float이 되게 만들었습니다.

**시간** — `measure_ms(repeat=3)`: 워밍업 5회 후 3회 평균

| 크기 | 연산 횟수(N²) | `mac()`(ms) | 1회 곱셈-누적당 | `mac_flat()`(ms) | 개선율 |
|---|---|---|---|---|---|
| 100×100 | 10,000 | 0.196 | 약 0.020µs | 0.186 | 약 5% |
| 500×500 | 250,000 | 5.481 | 약 0.022µs | 4.667 | 약 15% |
| 1000×1000 | 1,000,000 | 22.409 | 약 0.022µs | 18.705 | 약 17% |

*3회 실행 결과 1000×1000의 `mac()`은 22.4~22.7ms, 개선율은 16~18%로 안정적이었고, 100×100의 개선율만 3~12%로 흔들렸습니다.*

**메모리** — `tracemalloc`으로 생성 전후 차이 측정 (1MB = 10⁶바이트)

| 크기 | 패턴(`make_cross`) | 필터(원소마다 다른 float) | 패턴+필터 | 필터 원소당 | 필터를 `array('d')`로 |
|---|---|---|---|---|---|
| 100×100 | 0.09MB | 0.33MB | 0.42MB | 33.3B | 0.08MB |
| 500×500 | 2.11MB | 8.11MB | 10.22MB | 32.4B | 2.00MB |
| 1000×1000 | 8.86MB | 32.86MB | 41.72MB | 32.9B | 8.00MB |

**정확도** — 0.1을 N²번 더한 결과와 기대값(N²/10)의 차이

| 크기 | 더한 횟수 | 기대값 | 단순 누적 오차 | 상대 오차 | `math.fsum` 오차 | 1e-9 초과 |
|---|---|---|---|---|---|---|
| 100×100 | 10,000 | 1,000 | 1.6e-10 | 1.6e-13 | 0 | 아니오 |
| 500×500 | 250,000 | 25,000 | 8.3e-8 | 3.3e-12 | 0 | 예 |
| 1000×1000 | 1,000,000 | 100,000 | 1.3e-6 | 1.3e-11 | 0 | 예 |

**병렬화** — 1000×1000을 250행씩 4블록으로 나눠 `multiprocessing.Pool(4)`로 부분합을 계산 (각 3회 평균)

| 방식 | 시간(ms) | 단일 `mac()` 대비 | 워커 계산 시간(ms, 4개 중 최대) |
|---|---|---|---|
| 단일 `mac()` | 22.85 | 기준 | - |
| 같은 프로세스에서 4블록 순차 계산 | 22.66 | 약 1.0배 | - |
| Pool 생성 + 계산 + 종료 | 82.34 | 약 3.6배 느림 | - |
| Pool 재사용, 매번 블록 데이터 전달 | 31.46 | 약 1.4배 느림 | 6.20 |
| Pool 재사용, 데이터 전달 없음(워커가 블록 보유) | 6.33 | 약 3.6배 빠름 | 6.15 |

*`mac()`은 `len(pattern)`으로 행·열 범위를 함께 정하는 정사각 전제라, 블록에는 같은 `p[i][j] * f[i][j]` 인덱싱의 블록용 함수를 썼습니다. 마지막 행은 Pool initializer에서 워커가 같은 데이터를 직접 만들어 두고 호출 때 블록 번호만 받게 해, ④처럼 각 프로세스가 자기 행을 직접 읽는 상황을 흉내 냈습니다. 시작 방식은 macOS 기본값인 spawn, 논리 코어 12개입니다. 3회 실행 범위는 단일 22.6~23.2ms, Pool 생성 포함 81~86ms, 블록 전달 31.1~31.5ms, 전달 없음 6.3~7.5ms였습니다.*
*4블록 부분합의 합은 단일 `mac()`과 십자가 패턴에서 3.4e-13, 모든 칸이 0이 아닌 무작위 패턴에서 4.4e-9(상대 오차 1.8e-14) 달랐습니다.*

**시간 분석.** 1000×1000의 1회 곱셈-누적당 시간은 약 0.022µs로, "시간 복잡도 분석" 표의 13×13·25×25(약 0.020µs)와 거의 같습니다.
N²가 4배(500 → 1000)일 때 시간도 약 4.1배로 늘어, 고정 비용이 묻히는 큰 N에서 시간이 N²에 비례하므로 O(N²)가 그대로 유지됩니다.
병목은 연산 자체가 아니라 원소마다 반복되는 인터프리터 처리입니다. 원소 하나마다 반복 변수 갱신, 리스트 인덱싱 4번, 곱셈과 덧셈을 바이트코드로 하나씩 실행하고, 곱셈 결과와 누적값마다 새 float 객체를 만듭니다.
CPU의 부동소수점 곱셈 1회는 1ns도 걸리지 않으므로, 1회당 약 22ns 중 대부분이 이 처리 비용입니다.
필터를 `array('d')`로 바꾸면 값을 읽을 때마다 float 객체를 새로 만들어야 해서 `mac_flat()`이 18.7ms에서 31.3ms로 약 1.7배 느려졌는데, 이는 객체 생성이 병목의 큰 부분이라는 근거입니다.

**메모리 분석.** 필터처럼 원소마다 다른 float이면 원소당 약 32바이트(float 객체 24바이트 + 리스트의 참조 8바이트)가 들어, 1000×1000 행렬 하나가 약 32MB(측정 32.9MB)입니다.
`make_cross` 패턴은 모든 칸이 `1.0`/`0.0` 두 객체를 공유해 참조 8바이트씩만 차지하지만(8.9MB), `json.load`로 읽은 실수는 숫자마다 새 float 객체가 되므로 실제 데이터는 32바이트 쪽에 가깝습니다.
게다가 `json.load`는 파일 전체를 문자열로 읽은 뒤 한 번에 파싱하므로, 1000×1000 케이스 하나(패턴 + 필터 2개)만 넣어도 행렬만 약 100MB에 파싱 중에는 파일 텍스트까지 함께 메모리에 올라갑니다.
모드 1은 현재 3×3 전용이고, N×N으로 넓히더라도 1000×1000이면 숫자 1000개짜리 줄을 행렬 3개 × 1000줄 = 3000줄 입력해야 합니다. 형식 오류가 나면 그 행렬을 처음부터 다시 입력하는 구조라 더욱 비현실적이므로, 대규모 입력은 파일로만 받아야 합니다.

**정확도 분석.** 0.1을 단순 누적하면 더한 횟수가 100배(10,000 → 1,000,000) 늘 때 오차는 약 8,000배 커졌습니다. 누적값이 커질수록 한 번 더할 때 반올림되는 단위(ulp)도 커지기 때문입니다.
500×500부터 이미 현재 판정 기준인 1e-9를 넘고, 1000×1000에서는 1e-9의 1,000배 이상입니다. 같은 방식으로 누적되는 MAC 점수라면 수학적으로 동점이어도 UNDECIDED가 아닌 한쪽 승리로 판정될 수 있으므로, 크기와 무관하게 고정된 절대 epsilon은 큰 입력에서 깨집니다.
반면 상대 오차는 1000×1000에서도 1.3e-11로 작으므로, 점수 크기에 맞춰 기준이 커지는 상대 허용오차 `abs(a - b) <= max(rel_tol * max(abs(a), abs(b)), abs_tol)`(표준 라이브러리 `math.isclose`와 같은 식)를 쓰면 됩니다.
또는 `math.fsum`으로 합산하면 중간 반올림 오차를 보정해 세 크기 모두 오차가 0이었습니다(MAC에 쓰면 곱셈 1회의 반올림은 남지만 누적 오차는 사라집니다).

**우선 적용할 최적화 순서**

- **① 비교 정책을 상대 허용오차로 변경** — 성능이 아니라 정확성 문제라 최우선입니다. 아무리 빨라져도 판정이 틀리면 의미가 없고, 변경 범위도 `judge.py`의 `is_tie` 비교식 한 줄로 가장 작습니다. 뒤의 ⑤도 이 변경을 전제로 합니다.
- **② 평탄화** — 보너스 1에서 이미 `mac_flat`으로 구현해 두었으므로 바로 적용할 수 있습니다. 작은 크기에서 약 20~42%(보너스 표), 1000×1000에서 약 17% 빨라졌습니다. 다만 상수 배 개선이라 O(N²) 자체는 그대로입니다.
- **③ 표준 라이브러리 `array('d')`** — float 객체 없이 원소당 8바이트로 저장해 1000×1000 필터가 32.9MB에서 8.0MB로 약 4배 줄었습니다. 대신 읽을 때마다 float 객체를 만들어 MAC은 약 1.7배 느려졌으므로, 속도가 아니라 메모리가 한계일 때 쓰는 선택입니다. N이 더 커지면(10000×10000은 리스트로 약 3.2GB) 메모리가 먼저 한계에 닿기 때문에 이 순서에 둡니다.
- **④ 스트리밍** — MAC은 행별 부분합의 합(Σᵢ Σⱼ pᵢⱼ·fᵢⱼ)이므로 패턴과 필터를 한 행씩 읽어 부분합을 더하고 버리면 메모리가 O(N²)에서 O(N)으로 줄어듭니다. 단, 표준 `json` 모듈은 문서 전체를 한 번에 파싱하므로 한 줄에 한 행씩 쓰는 포맷(CSV, JSON Lines 등)으로 입력 형식을 바꿔야 해서 뒤 순서입니다.
- **⑤ 타일링/블로킹 + 병렬화** — 행렬을 블록으로 나눠 블록별 부분합을 `multiprocessing`으로 여러 프로세스에서 계산한 뒤 합산합니다. 기본 CPython(이 측정 환경 포함)은 GIL 때문에 순수 Python 반복문을 스레드로 동시에 실행할 수 없어 스레드로는 효과가 없습니다.
위 병렬화 표에서 계산 자체는 4프로세스로 약 3.6배 빨라졌지만(22.9 → 6.3ms), 그대로 적용하면 오히려 느렸습니다. spawn 방식은 워커마다 새 인터프리터를 띄우므로 호출마다 Pool을 만들면 약 3.6배 느렸고, 만들어 둔 Pool에 블록을 넘기기만 해도 약 1.4배 느렸습니다.
후자의 31.5ms 중 워커 계산은 6.2ms뿐이고, 나머지 약 25ms는 대부분 블록 데이터를 직렬화(pickle)해 워커로 보내는 비용입니다(데이터 전달이 없으면 계산 외 비용은 약 0.2ms). 따라서 병렬화는 ④와 합쳐 각 프로세스가 자기 행을 직접 읽게 해야 이득이 납니다.
또 4블록 합산은 무작위 패턴에서 단일 `mac()`과 4.4e-9 차이가 나 현재 기준 1e-9를 넘었으므로, 블록 분할 방식에 따라 판정이 바뀌지 않으려면 ①이 전제되어야 합니다.
- **⑥ 벡터화(NumPy)** — 이 미션은 외부 라이브러리를 금지하므로 적용하지 않았습니다. NumPy는 반복문을 C 코드로 내려 원소마다의 인터프리터 비용을 없애는 방식이고, 실제 NPU는 한 단계 더 나아가 수천 개의 MAC 유닛으로 이 곱셈-누적을 하드웨어에서 동시에 수행합니다. 이 시뮬레이터가 for문으로 순차 처리한 연산이 바로 NPU가 병렬로 처리하는 연산입니다.

## 보너스 (선택)

**1. 1차원 배열 최적화** — 2차원 행렬을 길이 N²의 1차원 리스트로 평탄화하고 단일 반복문으로 MAC을 수행합니다(`mac_flat`).
평탄화는 측정 구간 밖에서 수행하고, 동일 입력과 동일 반복 횟수(10회)로 비교했습니다.

| 크기 | 2차원(ms) | 1차원(ms) | 개선율 |
|---|---|---|---|
| 3×3 | 0.0004 | 0.0002 | 약 42% |
| 5×5 | 0.0007 | 0.0005 | 약 36% |
| 13×13 | 0.0036 | 0.0026 | 약 29% |
| 25×25 | 0.0127 | 0.0101 | 약 20% |

*개선율은 프로그램이 반올림 전 값으로 계산한 것이라, 표의 소수 4자리 값으로 다시 나누면 다르게 나올 수 있습니다.*

모든 크기에서 1차원 버전이 더 빨랐습니다. `pattern[i][j]`의 2단계 인덱싱과 행마다 내부 루프를 다시 시작하는 비용이 사라졌기 때문입니다.
개선율은 크기가 커질수록 줄어(3×3 약 42% → 25×25 약 20%), 행 단위로 드는 루프 재진입 비용이 원소 수에 비해 큰 작은 크기에서 1차원화 효과가 더 크게 나타나는 것으로 보입니다.
3회 실행에서 25×25는 16~20%로 비교적 안정적이었지만, 3×3은 22~42%로 흔들렸습니다. 측정값이 0.2~0.4µs 수준이라 10회 평균만으로는 타이머 잡음을 다 걸러내지 못하기 때문으로 판단합니다.
Python 리스트는 원소 객체에 대한 참조를 저장하므로, C 배열처럼 메모리 연속성에 따른 캐시 이득이 크게 나타나지 않는다는 점도 한계입니다.

**2. 패턴 생성기** — `make_cross(n)`, `make_x(n)`이 N×N 십자가/X 패턴을 생성합니다.
data.json에 없는 3×3 성능 측정과, 모든 크기의 성능 측정용 입력 패턴으로 재사용합니다.
