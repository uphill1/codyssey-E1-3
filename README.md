# Mini NPU Simulator

코디세이 Pre-course 미션 3. NPU가 수행하는 MAC(Multiply-Accumulate) 연산을 Python으로 직접 구현해,
십자가(Cross)와 X 패턴을 판별하고 크기별 연산 시간을 분석하는 콘솔 시뮬레이터입니다.
NumPy 등 외부 라이브러리 없이 Python 표준 라이브러리(`json`, `time`, `os`, `sys`)만 사용합니다.

## 실행 방법

```bash
python3 main.py                            # 1: 사용자 입력(3×3), 2: data.json 분석
python3 main.py samples/broken_data.json   # (선택) 스키마 오류 처리 검증용 데이터로 모드 2 실행
```

- Windows에서는 `python3` 대신 `python main.py`로 실행합니다.
- 프로젝트 루트에서 실행합니다. Python 3.8 이상.
- `data.json`은 `main.py` 위치 기준 상대 경로로 읽으므로 실행 위치와 무관하게 동작합니다.

## data.json 구조와 처리 규칙

| 항목 | 원본 형태 | 프로그램 처리 |
|---|---|---|
| `filters` 키 | `size_{N}` | N 추출 → 해당 크기 필터 그룹 |
| 필터 라벨 키 | `cross`, `x` | `Cross`, `X`로 정규화 |
| `patterns` 키 | `size_{N}_{idx}` | `split('_')[1]`로 N 추출 → `size_N` 필터 선택 |
| `input` | N×N 2차원 배열 | 키의 N과 실제 크기 일치 검증 |
| `expected` | `+`, `x` | `Cross`, `X`로 정규화 후 판정과 비교 |
| `meta` | 버전 정보 | 사용하지 않음 |

규칙을 위반한 케이스는 예외로 프로그램을 종료하지 않고, 해당 케이스만 FAIL과 사유로 기록합니다.

## 핵심 설계

- **MAC**: 이중 for문으로 `total += pattern[i][j] * filt[i][j]`를 N²번 수행합니다.
- **라벨 정규화**: 입력 시점에 `strip().lower()` 후 매핑 테이블로 `Cross`/`X`로 통일하고, 모르는 라벨은 `None` → FAIL 처리합니다. 콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준입니다.
- **판정 정책**: `abs(score_cross - score_x) < 1e-9`이면 `UNDECIDED`(모드 1에서는 "판정 불가"), 아니면 큰 쪽을 선택합니다.
- **성능 측정**: `time.perf_counter()`로 `mac()` 호출 구간만 감싸 10회 측정 후 평균(ms)을 냅니다. I/O는 측정 구간 밖에 두고, 초기 호출의 편차를 줄이기 위해 측정 전 5회 워밍업합니다.
- **실패 분류**: 모든 FAIL을 `데이터/스키마`, `로직`, `수치 비교` 중 하나로 태그해 출력합니다.

## 결과 리포트

### 실행 결과 요약 (공식 data.json)

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

**전체 6 / 통과 3 / 실패 3** — 실패 3건은 모두 `수치 비교` 분류이며, 데이터/스키마 실패와 로직 실패는 0건입니다.

### 실패 원인 분석

실패 3건은 코드 결함이 아니라 데이터가 의도적으로 동점이 되도록 설계된 케이스입니다.
size_5_1을 예로 들면, X 패턴 입력에 대해 Cross 필터는 가운데 한 칸(0.9)만 겹쳐 `1.0 × 0.9 = 0.9`가 한 번에 계산됩니다.
반면 X 필터는 0.1짜리 9칸을 차례로 누적해 0.9를 만듭니다. 0.1은 2진수로 정확히 표현되지 않는 근사값이라 9번 더하는 동안 오차가 쌓여 `0.8999999999999999`가 됩니다.
즉 수학적으로는 두 점수가 같지만, 계산 경로가 달라 약 1.1e-16의 차이가 생깁니다. size_13_2(차이 2.7e-15), size_25_1(차이 1.8e-15)도 같은 구조입니다.

만약 `>`나 `==`로 비교했다면 size_5_1과 size_25_1은 Cross, size_13_2는 X로 판정되어, 실제로는 동점인데 한쪽이 "이긴" 결과가 됩니다.
그 경우 FAIL 원인이 판정 로직 오류처럼 보여 잘못된 방향으로 디버깅하게 됩니다.
epsilon(1e-9) 비교를 적용하면 세 케이스가 UNDECIDED로 판정되고, expected와 달라 FAIL이 되지만 원인이 `수치 비교`로 정확히 분류됩니다.
1e-9는 이 데이터의 누적 오차(최대 약 3e-15)보다 충분히 크고, 의미 있는 점수 차이(최소 0.1 단위)보다 충분히 작아서 오차만 흡수하고 실제 차이는 구분합니다.

라벨 정규화가 없었다면 판정 결과 `Cross`와 expected `+`가 문자열로 달라 십자가 케이스(size_5_2, size_13_2, size_25_2)가 전부 FAIL이 되었을 것이고, 이는 `데이터/스키마` 문제입니다.
정규화를 입력 시점 한 곳에서 수행해 PASS 3건이 정상적으로 PASS로 집계되었고, 스키마 실패가 0건이 되었습니다.

스키마 검증 경로는 `samples/broken_data.json`으로 확인했습니다. 패턴 크기 불일치(2×3), 알 수 없는 라벨(`circle`), 대응 필터 없음(`size_7`), 키 규칙 위반(`pattern_1`)이 모두 프로그램 종료 없이 `데이터/스키마` FAIL로 기록되고,
공백·대문자가 섞인 `" CROSS "`는 정규화로 `Cross`가 되어 PASS, 기대값과 판정이 다른 케이스는 `로직` FAIL로 분류되는 것을 확인했습니다.

### 시간 복잡도 분석

| 크기 | 연산 횟수(N²) | 평균 시간(ms) | 3×3 대비 시간 | 3×3 대비 N² | 1회 곱셈-누적당 시간 |
|---|---|---|---|---|---|
| 3×3 | 9 | 0.0004 | 1.0배 | 1.0배 | 약 0.044µs |
| 5×5 | 25 | 0.0007 | 약 1.8배 | 약 2.8배 | 약 0.028µs |
| 13×13 | 169 | 0.0036 | 약 9.0배 | 약 18.8배 | 약 0.021µs |
| 25×25 | 625 | 0.0127 | 약 32배 | 약 69.4배 | 약 0.020µs |

*각 크기 10회 반복 평균. 측정 환경: Apple M4 Pro, macOS 26.3, Python 3.14.8. 3회 실행 결과가 5×5 한 번(0.0010)을 제외하고 소수 4자리까지 같았습니다. 절대값은 실행 환경마다 다릅니다.*

MAC은 N×N의 모든 칸을 정확히 한 번씩 방문해 곱셈 1회와 덧셈 1회를 수행하므로, 연산 횟수는 N²이고 시간 복잡도는 O(N²)입니다.
측정 결과도 크기가 커질수록 시간이 단조 증가해 이 추세를 따릅니다.
다만 3×3 대비 25×25가 N² 비율(69배)만큼이 아니라 약 32배만 느린데, 이는 함수 호출, `len()` 계산, 반복문 진입 같은 **크기와 무관한 고정 비용** 때문입니다.
작은 크기에서는 이 고정 비용이 전체 시간에서 차지하는 비중이 커서, 1회 곱셈-누적당 시간이 3×3에서 약 0.044µs로 가장 크게 나타납니다.
크기가 커질수록 고정 비용 비중이 줄어 13×13과 25×25에서는 1회당 시간이 약 0.021µs, 0.020µs로 거의 같아지며, 이 구간(169 → 625, 3.7배)의 시간 비율도 약 3.5배로 N² 비율에 가까워집니다.
즉 시간은 `T(N) ≈ a·N² + b` 꼴이며, N이 클수록 `a·N²` 항이 지배해 O(N²)이 드러납니다.
실제 NPU는 이 N²번의 MAC을 수천 개의 회로로 동시에 처리하지만, 이 시뮬레이터는 for문으로 순차 처리하므로 연산량 증가가 그대로 시간 증가로 나타납니다.

## 보너스 (선택)

**1. 1차원 배열 최적화** — 2차원 행렬을 길이 N²의 1차원 리스트로 평탄화하고 단일 반복문으로 MAC을 수행합니다(`mac_flat`).
평탄화는 측정 구간 밖에서 수행하고, 동일 입력과 동일 반복 횟수(10회)로 비교했습니다.

| 크기 | 2차원(ms) | 1차원(ms) | 개선율 |
|---|---|---|---|
| 3×3 | 0.0004 | 0.0002 | 약 42% |
| 5×5 | 0.0007 | 0.0005 | 약 36% |
| 13×13 | 0.0036 | 0.0026 | 약 29% |
| 25×25 | 0.0127 | 0.0101 | 약 20% |

*개선율은 프로그램이 반올림 전 값으로 계산한 것이라, 표의 소수 4자리 값으로 다시 나누면 다르게 나올 수 있습니다.*

모든 크기에서 1차원 버전이 더 빨랐습니다. `pattern[i][j]`의 2단계 인덱싱과 행마다 내부 루프를 다시 시작하는 비용이 사라졌기 때문입니다.
개선율은 크기가 커질수록 줄어(3×3 약 42% → 25×25 약 20%), 행 단위로 드는 루프 재진입 비용이 원소 수에 비해 큰 작은 크기에서 1차원화 효과가 더 크게 나타나는 것으로 보입니다.
3회 실행에서 25×25는 16~20%로 비교적 안정적이었지만, 3×3은 22~42%로 흔들렸습니다. 측정값이 0.2~0.4µs 수준이라 10회 평균만으로는 타이머 잡음을 다 걸러내지 못하기 때문으로 판단합니다.
Python 리스트는 원소 객체에 대한 참조를 저장하므로, C 배열처럼 메모리 연속성에 따른 캐시 이득이 크게 나타나지 않는다는 점도 한계입니다.

**2. 패턴 생성기** — `make_cross(n)`, `make_x(n)`이 N×N 십자가/X 패턴을 생성합니다.
data.json에 없는 3×3 성능 측정과, 모든 크기의 성능 측정용 입력 패턴으로 재사용합니다.
